Refinery Engineering AI Workbench

A fully local engineering assistant for a refinery: it reads the organisation's own manuals, SOPs and drawings, answers with evidence, runs real local tools, produces Word / Excel / PowerPoint deliverables under human sign-off — and can prove that nothing ever left the premises.

1. What this is, and how to start it

The workbench has two layers. The knowledge layer turns PDFs into structured, source-grounded knowledge (chapters, procedures, tables, engineering claims with their context, relationships). The agentic workbench sits above it: it classifies a request, resolves equipment tags, enforces access before retrieval, plans a DAG of specialist agents, verifies every statement against evidence, and returns typed answer blocks to a terminal, an HTTP API and a React web page.

Everything runs on one machine. Language models are open-weight models served by a local Ollama; OCR is an on-device ONNX engine; the vision model is local; code runs in a network-less sandbox; keys never leave a local key-management service; and a network monitor records every connection the host makes for the whole session into a tamper-evident log.

Why it is built this wayThe model is never the system's memory and is never trusted to invent engineering truth. Deterministic rules, structured knowledge, evidence checks and governance decide what may be answered; the model writes prose from evidence it is handed. Access control lives in the knowledge service and the release gate — below the prompt — so no wording can widen it.

Start it in five commands

# 1. Python environment (Python 3.10+, developed on 3.13)
python -m venv .venv && .venv\Scripts\activate && pip install -e ".[dev]"

# 2. Accounts and document tags (one-off). Seeds admin / manager / user.
python -m workbench setup-security

# 3. The API. The web page proxies /api to port 8077 (WebPage/vite.config.ts).
python -m workbench serve --port 8077          # add --tls or --mtls for local TLS

# 4. The web page
cd WebPage && npm install && npm run dev       # http://127.0.0.1:5173

# 5. Sign in
#    admin / Admin#2026      manager / Manager#2026      user / User#2026
#    (seeded; each is flagged must-change. Override with RWB_ADMIN_PASSWORD etc. before setup.)

Ollama with qwen3:4b and qwen3.5:2b gives model-written answers and vision; without Ollama every deterministic path still works (RWB_LLM=off). Interactive API docs are at http://127.0.0.1:8077/docs.

3. Knowledge layer & access (the foundation)

This existed before the September 2026 work and is documented in depth in docs/SECURITY.md and docs/ACCESS_AND_ANSWERS.md. The short version:

  • Three roles, three tags, one rule. user reads INTERNAL; manager adds CONFIDENTIAL; admin adds SECRET. A document may instead pin an explicit reader list (a compartment). An unclassified document defaults to SECRET.
  • Enforcement below the prompt. Every agent receives a GuardedKnowledgeService that drops records the role may not read — searches, tag lookups, graph walks, fetch-by-id, counts. Restricted content is never in the working context, so prompt injection has nothing to work with.
  • Escalation. A question that needs restricted material gets an answer from what is readable plus an automatically raised access request. The approver reads the exact passages, and approval mints a signed, single-use, short-lived key bound to one person, one question and one record list.
  • Release gate. The finished answer is re-checked: every citation readable, every tag resolvable, every figure present in evidence. A failure withholds the answer and is logged.

Demo script

  1. Sign in as user; open Knowledge: the CDU operating manual branch is locked and reports no size.
  2. Ask "What is the normal flow rate of the crude charge pump?" — the answer names how much restricted material bears on the question and the request id raised for you.
  3. Sign in as admin; open Access; read the passages; approve. Copy the one-time key.
  4. Back as user, re-ask the exact question with the key: those records, and nothing else, are released; the key is spent.
  5. python -m workbench security-check --passwords red-teams every role against your own documents.

4. Multi-model routing

Several open-weight models are available at once and the router picks one per call. No agent says "task X → model Y": an agent names the purpose of a call (compose_answer, classify, vision, plan_refine, tool_agent …), the router maps that to a task kind, scores every registered model on that kind, discards models that are not installed, penalises models that would spill off the GPU (and, on the 4 GB "fast" budget, models that think at length), keeps the resident model when the gain is small (a swap costs 5–15 s on a 4 GB card), and records the decision.

Registering a model

A model is one entry in workbench/models/registry.yaml or, without touching the repository, in data/workbench/models/registry.local.yaml (same shape; same name replaces, new name adds). Pull it into Ollama (or import a signed package, §9) and it is routable at the next start — or immediately via POST /models/register.

models:
  - name: qwen2.5-coder:7b
    size_gb: 4.7
    context: 16384
    modalities: [text]
    min_vram_mb: 6000
    capabilities: {code: 0.92, tool_agent: 0.72, reasoning: 0.62, classification: 0.55}
    notes: Coding specialist

5. Agentic tools & the sandbox

An agent run is not a chat reply: it plans, calls real local tools, reads the result and iterates, within a bounded number of steps. Each session has its own workspace directory (data/workbench/workspace/<user>__<session>/); every tool call is appended to the chained tool_calls.jsonl with the hash of its arguments, its outcome and timing.

The named tools

ToolWhat it does
read_file, write_file, list_filesfiles inside the session workspace only — absolute paths, .. and symlink escapes are refused
run_pythonruns code in the sandbox; optional test_* functions decide whether the run is verified; artefacts land under sandbox/<run_id>/
spreadsheet_read, spreadsheet_writeread sheets and formulas; write cells, rows or appended rows; strings starting with = are written as formulas
search_documentsthe organisation's own manuals, SOPs, standards and correspondence — passages, documented values or procedures — through the same guard as a question, so only readable documents are searched
calculatedeterministic arithmetic with every step shown; variables, math functions, and unit conversion through the plant unit tables
ocr_image, describe_imageon-device OCR with per-line confidence; the local vision model for P&IDs, handwriting, photos, gauges
make_docx, make_xlsx, make_pptxWord / Excel / PowerPoint from a released answer or from Markdown content, stamped "pending human sign-off"

[calculate] ok=True 1 ms
… = 7.8838

$ python -m workbench agent "calculate 2*(3+4)"

With Ollama up, the agent loop asks the routed model for the next tool each iteration (purpose="tool_agent"); without it, a deterministic planner recognises the common shapes (calculate, run python, search, read/write/list files, read spreadsheet). A failing tool becomes a failed iteration, never an exception.

The sandbox

run_python and POST /sandbox/run execute code in a fresh interpreter under these controls:

  • No network. socket.socket, create_connection, getaddrinfo, ssl, urllib, http.client are replaced before user code runs; an attempt raises PermissionError, the destination is recorded in egress_attempts and the run is marked limit_hit="egress".
  • No dependencies fetched at run time. -s -S hides site-packages; only the stdlib allow-list and a checksummed vendor directory (workbench/sandbox/vendor/manifest.json) are importable. If a vendored file changes, the manifest fails verification and the vendor path is refused. Banned outright: subprocess, ctypes, multiprocessing, requests, httpx, asyncio, pip, signal, mmap and others.
  • Bounded. Defaults: 20 s wall, 20 s CPU, 512 MB, 20 MB written, 1 process, 200 KB of output. On Windows a job object enforces memory, CPU time and process count; a psutil watchdog kills at 1.5× the memory cap as a second line.
  • Ephemeral. A new temporary directory per run, destroyed afterwards; outputs are returned as hashed artefacts.
  • Verified means: static analysis passed (syntax, banned imports, banned calls such as eval/exec/os.system, pyflakes) and the task's own tests passed in a second fresh run.
  • Deterministic. PYTHONHASHSEED=0, random.seed(0), the manifest hash on every result.
  • Logged. One chained entry per run in data/workbench/sandbox/runs.jsonl; GET /sandbox/runs.
$ python -m workbench sandbox-run script.py --tests tests.py
run sb-… backend=subprocess exit=0 ok=True verified=True limit=none 412 ms peak 9.1 MB cpu 0.03s
tests: 2/2 passed
workdir destroyed: True; run-log entry 3f9a…
Honest limitThe Docker backend (--network none --cap-drop ALL --security-opt no-new-privileges --read-only --memory --cpus 1 --pids-limit, pre-vendored image refinery-sandbox:latest) is implemented in sandbox/runner.py but Docker is not installed on this host, so it is untested here. 6. Multimodal intake

Scanned PDFs, photographs, P&IDs and handwritten notes come in through one pipeline (intake/pipeline.py):

  1. Text layer or scan? A PDF page with a text layer keeps it (confidence 1.0, noted "text layer"); a scanned page is rasterised with pypdfium2 and OCR'd.
  2. OCR on device. RapidOCR (ONNX, CPU): every line comes back with its text, bounding box and a confidence. On the sample chapter data/sample docs/test.pdf, forcing OCR on page 2 gave 43 lines at mean confidence 0.996 in 7.4 s.
  3. Vision where OCR cannot help. The routed vision model (qwen3.5:2b here) is asked with a purpose-specific prompt: a P&ID (list legible tags, lines, instruments, flow direction — never invent a tag), handwriting (transcribe literally, mark [illegible]), a gauge (the reading and units, or "not legible"), a photo. Vision calls take 35–55 s on the 4 GB card, so the upload path makes at most one.
  4. Flag, never pass through. Every OCR line under the threshold (0.6 by default) and every [illegible] span lands in flagged. Uploads and POST /intake turn the numbers found into a review draft whose low-confidence figures are already flagged (§7) — this is the "misread pressure value" case.
$ python -m workbench intake "data/sample docs/test.pdf" --max-pages 3 --vision-calls 1
$ python -m workbench intake photo_of_gauge.jpg --purpose gauge
$ python -m workbench intake scan.pdf --no-vision            # OCR only, fast

In the chat, attaching an image runs the same intake: the OCR text and the vision note become session notes the resolver can use, and the response carries the flagged lines and the draft id.

7. Deliverables & human review

The output of a request can be a file, not a chat reply. Any released answer (kept whole under data/workbench/responses/, private to the person it was released to) can be exported as Word, PowerPoint, Excel or Markdown. Every export is registered as a draft that is pending_signoff from the moment it exists.

What the files contain

  • Word (.docx): title, classification in the header and footer of every page, a red "DRAFT — pending human sign-off" banner, the answer prose, each typed block (tables with a citation column, numbered steps, safety callouts, comparison and limit tables), a "Calculation steps" section, a Provenance table (figure, value, unit, document, page, source excerpt), the Evidence list, and an Audit line.
  • Excel (.xlsx): sheets Answer, Values (one row per figure with document and page), one sheet per table block, Calculation — where a step is arithmetic between values on the sheet it is written as a live formula (for the limit check: =(C5-C3)/C3*100, =C5<=C4) next to the literal value so a reviewer can recompute — Provenance, Evidence, Audit.
  • PowerPoint (.pptx): title, answer bullets with numbers verbatim, one slide per major block, Provenance and Evidence slides, and a footer on every slide with the classification and the pending state.

The review workflow

  1. Provenance-linked figures. The draft extracts every numeric value from the answer's blocks and joins it to its evidence: document, page, chunk or claim id, and the source sentence. A reviewer checks a specific claim against a specific line, not the whole document.
  2. Confidence-based flags. A figure is flagged when it has no evidence, when it came from OCR or vision under the confidence threshold, or when it is LLM-derived rather than verbatim (grounding < 1). The value an engineer typed into a limit question is marked "requester" and is not treated as evidence.
  3. Mandatory resolution. Each flag is resolved as accepted, corrected (a corrected value is required) or removed, by name, with a note.
  4. Sign-off blocked until clean. sign_off raises SignoffBlocked — HTTP 409 listing the open flags — while any flag is open; it needs a manager or administrator; a blocked attempt is written to the security audit as signoff_blocked.
  5. Visible pending state. Every draft and every file says so until a person signs it off; nothing is auto-approved. The draft registry's event log is hash-chained.
$ python -m workbench responses                      # answers on record
$ python -m workbench export resp-… --format xlsx
written data/workbench/deliverables/admin/…xlsx (…bytes)
draft draft-…: status pending_signoff; 6 figure(s), 0 flagged for review
DRAFT — pending human sign-off
$ python -m workbench drafts -v
$ python -m workbench draft-resolve draft-… fig-… corrected --value 24.45 --note "checked p.2"
$ python -m workbench draft-signoff draft-…          # exit code 2 and the open flags while any remain

The OCR engine reads even handwriting at 0.96–0.99, so the bar decides how much human attention the output attracts.

8. Vault: envelope encryption per branch

Three layers of key, each wrapping the one below (security/vault.py):

master key (MK)           32 bytes; data/workbench/security/kms/master.key  or  RWB_MASTER_KEY_HEX
 └─ role wrapping keys    one per role (user / manager / admin), versioned, wrapped by MK   kms/keyring.json
     └─ branch content keys   one per branch (document), never stored raw;
                              wrapped once PER ROLE that may read the branch             kms/branches.json
                                └─ the branch's index, AES-256-GCM                       data/workbench/vault/<branch>/index.enc
  • Why envelope: the data is encrypted once. Who can read it is decided by which roles hold a wrapped copy of its content key. Rotating a role's key re-wraps a few dozen 32-byte keys, not gigabytes; revoking a role from a branch deletes one wrapped copy. Both are instant and neither touches the ciphertext. Associated data names the branch, role and key version, so a wrapped blob cannot be swapped between them.
  • Local KMS. Everything under data/workbench/security/kms/; the master key can come from RWB_MASTER_KEY_HEX so it lives on a removable token plugged in only while the server starts. Every create / wrap / rotate / revoke is a chained key_events.jsonl entry.
  • Session-scoped decryption. With RWB_VAULT=on no branch is loaded at start. When a session signs in, its keyring unwraps the content keys its role holds and those branches are decrypted into this process's memory and join the knowledge service. Keys are held as bytearray objects, zeroed on logout; when the last session with a key for a branch signs out, the branch is dropped from memory. Before an administrator signs in the CDU manual is not in the process at all. Plaintext is never written to disk by any vault function; seal --shred overwrites and deletes the plaintext index cache after sealing.
$ python -m workbench vault seal --shred        # administrator; one line per branch with its roles
sealed CDU operating manual        4520134 ->  4520178 bytes  roles admin
sealed Crude desalter               219003 ->   219047 bytes  roles manager, admin
$ set RWB_VAULT=on && python -m workbench serve --port 8077
$ python -m workbench vault status
$ python -m workbench vault rotate manager
$ python -m workbench vault revoke "Crude desalter" manager
What the demo showsGET /vault as user lists can_unwrap without the CDU manual; as admin it lists it, and branches_in_memory shows the branch appearing after the admin signs in and disappearing after the last admin signs out. After rotate every existing keyring is wiped; after revoke that role's wrapped copy is gone and the branch closes for it.
Scope of the sealingThe vault seals the workbench's derived branch indexes (the searchable form the answers come from). The knowledge layer's own artefacts under data/knowledge and data/parsed are the ingestion pipeline's output and are not sealed by this command; in a deployment they sit on the same encrypted volume or are sealed the same way.

9. Sovereignty: proving the air gap

"Nothing leaves the premises" is demonstrated, not claimed, three ways at once.

In-process egress guard

sovereignty/egress.py wraps socket.connect, connect_ex and create_connection in the workbench process. A destination that is not loopback, not a private range (10/8, 172.16/12, 192.168/16, link-local and IPv6 equivalents) and not on the allow-list raises EgressBlocked before any packet leaves, and the attempt is chained into egress.jsonl. The model libraries' offline flags (HF_HUB_OFFLINE, TRANSFORMERS_OFFLINE, …) are set, so a missing weight file fails loudly instead of quietly reaching Hugging Face. The allow-list is sovereignty.allowed_hosts in workbench/config.py (127.0.0.1, ::1, localhost) plus the hosts of the configured Ollama URL and Neo4j URI, which sovereignty/service.py adds at start-up; private ranges pass regardless. On by default; RWB_AIRGAP=off disables it.

Live network monitor + immutable connection log

sovereignty/netmonitor.py samples the host's socket table, interface state and traffic counters every 2 s for the whole session and writes every new connection (process, local and remote address, state, class loopback/private/external), every interface up/down transition and periodic traffic summaries to the chained connections.jsonl. External connections made by the workbench, its children and Ollama are counted separately from other programs on the host.

$ python -m workbench sovereignty
VERDICT: egress guard installed; 27 external connection(s) by other programs on this host;
         none by the workbench or the model server; all audit chains intact
network monitor: running=True samples=2 connections=89 external(host)=27 external(workbench)=0 uplinks up 2/6
   UP   Wi-Fi                        192.168.196.96
   DOWN Ethernet                     169.254.241.67
chained logs:
   ok  security audit                           922 entries  chain intact
   ok  connection log                           738 entries  chain intact
   ok  run audits (422 conversations)         14797 entries  all intact
Reading it on a developer laptopThe output above was captured on the development machine, where a browser and other programs hold external connections. The verdict counts the workbench's own; on the air-gapped demo host the host-wide count is expected to be zero too.

Physical disconnection

Run python -m workbench sovereignty --watch 5 and pull the uplink. The next sample logs interface_down with a timestamp, the status line reads DISCONNECTED and physically_disconnected becomes true; every question asked from then on answers exactly as before. Plug it back and interface_up is logged. A dashboard can be misread; a pulled cable and a timestamped log entry cannot.

Hash-chained logs

sovereignty/hashchain.py: every entry carries seq, ts, prev_hash and hash = SHA-256(seq | ts | prev_hash | canonical JSON). Editing, deleting or reordering any past entry breaks every hash after it, and verify() names the first bad entry. One trust boundary and one operator means this gives the tamper-evidence a ledger is known for without a distributed consensus solving a problem the deployment does not have. Chained: the security audit, every conversation's run audit, connections, egress, routing, sandbox runs, KMS key events, model updates, draft events, tool calls. Logs written before chaining existed are chained retroactively once, with a chain_migrated marker that says so. Appends take an OS-level lock so two processes cannot fork the chain.

$ python -m workbench audit-verify          # exit code 2 if any chain is broken
$ curl -X POST -H "Authorization: Bearer …" http://127.0.0.1:8077/sovereignty/verify

Signed, checksum-verified model packages

New open-weight models arrive as packages — a directory or tar with a Modelfile, the weight files, a MANIFEST.json (name, version, per-file SHA-256 and size, signer key id) and MANIFEST.sig (Ed25519 over the canonical manifest). Verification requires: the signer's public key in the local trust store, the signature recomputing, every listed file matching its hash and size, no file missing, no unlisted file. Import refuses on any failure and otherwise runs ollama create name:version -f Modelfile from the local files — never a download. Every verification and import is a chained model_updates.jsonl entry.

$ python -m workbench packages keygen release-2026            # on the signing machine
$ python -m workbench packages sign ./qwen-pkg --private-key … --key-id release-2026 --name qwen3 --version 4b
$ python -m workbench packages trust release-2026.pub release-2026   # on the air-gapped host
$ python -m workbench packages verify ./qwen-pkg
$ python -m workbench packages import ./qwen-pkg --dry-run
$ python -m workbench packages log

Internal TLS / mTLS

security/tls.py creates a local CA and server/client certificates (EC P-256) under data/workbench/security/tls/ on first use. serve --tls serves HTTPS; serve --mtls additionally requires a client certificate signed by that CA, so a compromised process on the same host cannot talk to the API without the client bundle. GET /vault/tls reports the fingerprints and whether TLS/mTLS is active.

12. The 15-minute demonstration

  1. Locked branches (1 min). Sign in as user. Knowledge page: the CDU manual is locked, no size shown. Ask "What is the normal flow rate of the crude charge pump?" → refusal with the count of restricted records and an access request id.
  2. Escalation (2 min). Sign in as admin, Access page, read the passages, approve → one-time key. As user, re-ask with the key → those records only; the key is spent.
  3. Air gap (3 min). python -m workbench sovereignty --watch 5. Show external(workbench)=0. Pull the uplink → DISCONNECTED, interface_down logged. Ask a question — same answer. Plug back in. GET /sovereignty for the chain verification.
  4. Sandbox (2 min). POST /sandbox/run with import socket; socket.create_connection(("8.8.8.8",53)) → egress_attempts, limit_hit: egress, workdir destroyed. Then a real task with tests → verified: true.
  5. Deliverable under review (3 min). Ask the limit question ("…operating at 520 m3/h. Is this acceptable?"). Export to Excel: open the Calculation sheet's live formula. Upload a photo of a gauge (or use /intake) → a flagged low-confidence figure. Try to sign off → 409 with the flag. Correct it with the value from the source line → sign off as manager.
  6. Routing (2 min). Models page / workbench models: capability table, who wins each kind. workbench route "Read the scanned P&ID, calculate the margin and write a note" → three sub-tasks, vision to qwen3.5:2b, calculation to the deterministic tool. Open an answer's audit block: models_used.
  7. Vault (2 min). vault seal; GET /vault as user vs admin (can_unwrap); with RWB_VAULT=on, branches_in_memory before and after the admin signs in; vault rotate manager; vault revoke "Crude desalter" manager → the manager's key is gone.
